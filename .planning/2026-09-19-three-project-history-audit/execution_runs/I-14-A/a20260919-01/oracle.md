## 2. Frozen measurement rules

- **M1 command total duration** — wall time of the whole probe process, reported as
  `windows.command_total_seconds`. Never used as a latency sample.
- **M2 business latency** — per successful resolve call, reported as `windows.slo_window_seconds`
  (the sum) and the percentile inputs. Failed calls are **not** latency samples.
- **M3 RSS sampling window** — `windows.rss_sample_window_seconds`, the span from the first to the
  last collected sample of the child that the peak belongs to, plus `rss_sample_count` and
  `rss_sampled_pids`. Independent of M1 and of `quick_check`.
- **M4 quick_check** — a **separately labelled** window, `windows.quick_check_seconds`, measured
  outside the SLO window, with its own `quick_check_returncode`. On the production catalog
  `PRAGMA integrity_check`/`quick_check` is minutes-scale and is deliberately not run by the fast
  release gate (`RF/tools/release_readiness.py:61-65`), so conflating it with the resolve latency
  would corrupt the SLO number.
- **M5 failure accounting** — success count and failure count are reported separately
  (`calls.succeeded` / `calls.failed`). A failed request is never dropped-and-forgotten to make the
  service look SLO-compliant (card clause 5).
- **M6 unmeasured ≠ zero** — `peak_rss_gb` is `null` with `peak_rss_source: "uncollected"` when no
  sample was collected; `0.0` means a sample was collected and the process really reported zero.
- **M7 synthetic memory is not an RSS oracle** — the fixture's self-reported allocation is compared
  against the sampler's reading only as an order-of-magnitude sanity check, never as a precise RSS
  oracle (card clause 3).
- **M8 budgets untouched** — `exact/latest/bundle p95 = 5.0`, `peak_rss_gb = 2.0`. Changing a budget
  requires an independent reason and is explicitly out of scope (card clause 4).
- **M9 this card proves the meter, not production.** Passing here grants no production SLO
  qualification; that needs I-16's real measurement and I-14-B's natural-time observation.

## 6. Errata against this oracle (recorded, not silently rewritten)

**R1-erratum (2026-09-20, during the first E1c run).** Section 3 said "the peak's PID must equal the
reported child PID" and section 4 E1c said `rss_sampled_pids == [<fixture pid>]`. That is wrong on
this platform: **`subprocess.Popen.pid` is not the PID of the process that runs the fixture script.**
A direct measurement (recorded in `after/cmd-E1c/pid-relationship.json`) shows `popen.pid = 48684`
while the child script's own `os.getpid()` is `41808`; the fixture scripts run in a descendant of the
process Windows reports from `CreateProcess`. This is exactly why the sampler must walk the process
*tree* rather than read one pid.

The expectation is therefore restated, **before** the re-run, as: the sampler's `rss_sampled_pids`
must *contain* the fixture's self-reported `os.getpid()` (identity of the measured process), and must
also contain the `Popen` pid (the tree root). Both are checked in `run_probe_cases.py`
(`fixture_pid_is_in_samples`, `rss_pids_include_child_pids`). No expectation was weakened: the new form
is strictly stronger about *which* process was measured, because it now pins the process the fixture
itself can attest to.

**E1c sample-count floor.** The original `rss_sample_count >= 1` was raised to `>= 10` for the
~1.6 s F3 fixture at a 50 ms interval. This is a *tightening*: with the old floor a single lucky read
would have passed. The measured value is recorded in `after/E1c-F3-alive-allocate/report.json`.

**E2 reachability.** Section 3's F4 control ("exits too fast to sample") does **not** reliably produce
zero samples: the sampler takes its first reading immediately after `Popen` returns, so a fast child
still yields exactly one live sample. F4 is therefore recorded as a *positive* control
(`E3-F4-instant-exit`: fast child still sampled, `peak_rss_source == "live_sample"`), and the
no-sample branch is exercised deterministically through `--rss-sampler none`
(`E2-F3-sampler-disabled`: `peak_rss_gb is null`, `peak_rss_source == "sampler_disabled"`, and the run
carries an explicit "peak RSS not measured" breach). Both cases were re-frozen here before the run
that produced them; the earlier names `E2-F4-instant-exit` / `E3-F3-sampler-disabled` appear only in
superseded scratch output.

**E7 scope limit (recorded after the first bundle control run).** The `copied_from_exact` refusal path
triggers only when the supplied bundle list has the *same numbers* as this run's exact latencies. A
file built from a *previous* run's numbers is measured on its own values and will not match
(measured: `identity_check.verdict == "independent"`, `p95` 0.0849 s vs the exact run's own values).
That is honest — run-to-run jitter makes cross-run numeric equality unreachable — but it means the
decisive control for the card's clause 6 is the **structural** one: the production tool contains
`bundle = exact[:]` and no bundle measurement at all, while the patched tool contains no such alias and
requires an explicit `--bundle-measurement`. Both are recorded in
`after/E7b/verdict.json`; the direct rule check is `E7-F4-no-bundle-measurement` (unmeasured bundle
⇒ breach ⇒ not green).

## 8. decision.md trigger (specialist decision, not self-accepted)

D1 — RSS peak measurement method on Windows: (a) `psutil.Process.memory_info().peak_wset` sampled per
child, vs (b) `rss` sampled live and maxed, vs (c) a private `GetProcessMemoryInfo` ctypes call. This
card must implement one, record which, and hand the choice to the ops reviewer (card clause 3: "单独
冻结采样间隔、平台可用的 peak 方式和测量误差规则，由运维 reviewer 决定"). Implementer position:
`rss` sampled live at a fixed interval, peak = max over samples, because `peak_wset` mixes
working-set peak semantics with sample timing and is not comparable across platforms.

### 9.1 F-I14A-02 — what the E5 baseline really shows

Source fact (unchanged, re-verified by the reviewer): the unmodified tool never inspects the child's
return code — `before/cmd-E5/../tool_prod/slo_probe.py` calls `subprocess.run(...)` and discards the
result, and `"returncode"` does not appear in its `_resolve` body. So the rc is **unobservable** to it.

New evidence (measured this pass, recorded in `before/cmd-E5b/`): with `text=True` and **no** explicit
`encoding`, the probe's own reader thread raises
`UnicodeDecodeError: 'utf-8' codec can't decode byte 0xd4 in position 11` while decoding the child's
stderr (the child writes GBK-encoded Chinese on this host), **six times** for three samples — once per
pipe. The exception is swallowed inside `subprocess._readerthread`, so the probe still exits 0 with
`breaches: []` and a report = timing + `peak_rss_gb` + `bundle_proxy` only (no `per_call`, no rc field).
The tool therefore cannot bind a child's failure to its own verdict **even in principle**: the channel
that would carry the evidence is the channel that fails to decode.

`before/cmd-E5/report.json` is the earlier run kept for continuity; `before/cmd-E5b/report.json`
(sha256 `15f522deb4214257aea053d8eb1801449e77669661c0e034998f9aca8a4bf440`) is the reproducible one,
with `before/cmd-E5b/stderr.txt` holding the six exceptions.

### 9.2 F-I14A-04 — the corrected expectation

Section 4's E1a/E1b rows said `calls.failed == 1`. The harness invokes the probe with `--samples 3`,
which issues **3 exact + 3 latest = 6** resolve calls, so the frozen expectation is `calls.failed == 6`
with `failed_kinds == {subprocess_rc: 6}` (E1a) and `{business_status: 6}` (E1b). The measured values
were already 6/6; only the oracle's written number was wrong. The per-case raw probe exit codes are
unchanged (4 for both).

### 9.3 F-I14A-05 — `catalog_dir` parser boundaries (for the D2 signer)

`config_catalog_dir()` handles exactly the forms present in the real configs: a top-level scalar,
quoted or bare, with `${PROJECT_ROOT}` / `${USER_PROFILE}` expansion and inline `#` comments. It does
**not** handle block scalars (`|`, `>`), inline mappings, anchors/aliases or escape sequences; on a
residual `${` it raises `ValueError`, which the binding treats as inconsistent and refuses with
**exit 3**. The failure mode is deliberately closed (refuse, never guess), and this limitation is now
listed as a known limitation for the D2 signature.

### 9.4 M3/M7 addendum (F-I14A-03)

**M3 (amended):** the reported peak is the maximum over samples of the **sum of `rss` across the
sampled process tree** (`Popen` pid plus all descendants, since on this platform the measured program
runs in a descendant). It is therefore a **conservative overestimate** of the measured program's own
RSS by whatever the launcher and any helper hold — measured here at ≈11 MB (0.267 GB summed tree vs
256 MB declared by the fixture). `peak_pid` is populated only when a sample covered exactly one pid;
otherwise it is `null` and `peak_tree_pids` carries the full set (6/6 E1c calls had 2 pids).

**M7 (amended):** a synthetic allocation is compared to the sampled peak only by order of magnitude,
and the known overestimate above is part of that comparison — it is not an RSS oracle and must never be
used to certify a budget value.
