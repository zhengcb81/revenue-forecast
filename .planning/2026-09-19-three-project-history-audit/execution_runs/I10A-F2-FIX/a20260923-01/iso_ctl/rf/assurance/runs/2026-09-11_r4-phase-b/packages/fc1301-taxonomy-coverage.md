# 工作包：FC-1301 词表门的覆盖面（立项，owner 2026-09-13 裁定第 7 条）

> **状态 = 已开工（owner 2026-09-15「都要」）**：只读前置已完成（见 §7），实施待下一步。

> **状态 = 已立项、未实施。** 本包只界定范围与验收；实施需 owner 一次 go/no-go（它会改 `observability.REASONS` 与 taxonomy 版本号，属**产品改动**）。
> 来源：F-B01-9 表第 1 行处置时登记的缺口——词表门**只识别两种关键字写法**，解析器里大量 reason 用**元组位置**写法，门**看不见**它们。

## 1. 问题（可复核）

- 门的位置：`company-wiki/tests/contract/test_fc1301_reason_taxonomy.py`（CI 每个 Python 版本都跑）。
- 门认得的写法：`reason="x"`、`_reject(..., "x")` 两种关键字形式。
- 门**不**认得的写法（实测存在）：以**位置参数**传 reason 的调用点，例如解析器的构造式把 reason 放在元组里。
- 后果：**未注册**的 reason 码可以长期存在而不被门拦下（F-B01-9 里我自己的 `not_found` 就因为恰好用了关键字写法而被拦下 —— 门的方向对，但**覆盖面**是漏的）。

## 2. 已实测的事实（写包时复核）

| 事实 | 证据 |
|---|---|
| 解析器侧至少 4 个 reason 未注册 | `not_readable` / `hydration_required` / `content_sha256_mismatch` / （B02 时代）`path_outside_configured_roots`（后者已改用已注册码） |
| 门的实现只按关键字匹配 | `test_fc1301_reason_taxonomy.py` 的扫描模式 |
| 注册表与版本号位置 | `src/company_wiki/source_catalog/observability.py`：`REASONS` + 顶部 taxonomy 版本 |

## 3. 范围（实施时）

1. **加宽门的覆盖面**：扫描改为 **AST**——凡 `Call` 中实参含字符串字面量且该调用被判定为"reason 传递点"（按被调函数名/参数名列表）即纳入；位置参数与关键字参数同等。
2. **补齐注册**：把实测未注册的码要么注册（带语义说明），要么把调用点改为已注册码（二选一，逐条给理由）。
3. **版本号**：注册表变化 ⇒ 按既有约定顶 taxonomy 版本；**跨仓影响必须先查**（filing-fetch 是否消费该版本号——属跨仓合同）。
4. **负例**：新增"故意用未注册码 + 位置写法"的用例，必须**红**（证明加宽真的生效）。

## 4. 明确不做

- 不改解析行为、不改 reason 语义、不动 B 阶段已冻结的导出面。
- 不把门扩到"任意字符串都是 reason"（会淹掉门）。

## 5. 验收（可证伪）

- [ ] 门在**位置写法**下能报出未注册码（负例红、正例绿）。
- [ ] 现存 reason 全部**已注册**或**已改写**，逐条给出处置。
- [ ] taxonomy 版本号已顶，且**跨仓消费点已核对**（有结论，不假设）。
- [ ] 全量契约套件 + 覆盖率/复杂度棘轮 + 三版本 CI 全绿。
- [ ] 独立复审一轮（按 §11：每步一次），处置表入库。

## 6. 风险 / 未知

- **跨仓**：版本号被消费时，顶版会连带影响 filing-fetch 的合同测试（需先只读查证）。
- 加宽后可能**一次暴露数十处**未注册码 ⇒ 需要"注册 or 改写"的批量处置，属真实工作量而非门的问题。
- AST 判定"reason 传递点"若过宽，会把普通字符串误判为 reason ⇒ 需一份显式的调用点白名单，并**写在门里**（可复核）。
