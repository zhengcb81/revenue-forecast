## 2. 缺陷①：`scripts/model_registry.py:335` 静默补 0

**盘上原文**（第 335 行）：

```python
        values = drivers.get(driver, [spec.defaults.get(driver, 0.0)] * len(years))
```

**行为**：调用方**省略**某个 driver 时，取值逻辑回落到 `spec.defaults.get(driver, 0.0)` —— 该 driver **没有声明缺省值**时**静默取 `0.0`**，并按预测年限长度铺开。该行**不含 `raise`**。

**实测复现**（`P-4`，本轮实跑，非转录）：

| 臂 | 输入 | 输出 |
|---|---|---|
| 省略 | `{"units":[100,110], "unit_revenue":[10,10]}`（**不含** `other_revenue`） | `[1000.0, 1100.0]` |
| 显式 0 | `{"units":[100,110], "unit_revenue":[10,10], "other_revenue":[0.0,0.0]}` | `[1000.0, 1100.0]` |

**两条臂逐元素相同** ⇒ **「省略」与「显式传 0」在结果上不可区分**。

**这为什么是缺陷**：省略一个驱动，语义上通常是「我没打算给它赋值 / 我忘了」，而 `0.0` 是一个**具体断言**（该科目本期为零）。把前者静默当成后者，等于**替调用方作了断言**，且这个断言**不体现在任何输出里** —— 预测结果与「我明确认为其他收入是 0」完全一样，事后无法从产物区分「我忘了填」和「我确信是 0」。这类静默补值在收入预测里尤其危险：`other_revenue` 被默默归零，模型照常出数、照常通过校验。

**裁定要求的正确行为**：**省缺即抛 `ModelRegistryError`**。

**炸伤半径**（两个口径都对，见 §3）：

| 口径 | 槽位数 | 涉及模型数 |
|---|---|---|
| **裁定的口径**：`optional` 槽位中**未声明缺省值** | **31** | **24** |
| 全注册表口径：`required + optional` 中未声明缺省值 | 156 | 31 |
| 注册表模型总数 | — | 31 |

**`defaults.get(driver, 0.0)` 在全文中仅出现 1 次**（第 335 行），即**这条静默补零的路径只有一条**，没有第二处平行实现。

**一个边界情况（必须写进卡里）**：`_spec` 的构造校验（第 40 行）已经要求 `defaults` 必须是 `optional` 的子集，所以**声明过缺省值的** optional 驱动（如 `timing_factor: 1.0`）**走的是声明值，不是 0.0** —— 缺陷只吃**未声明缺省值**的那 31 个槽位。修复时若一律改抛错，会**连带把「有声明缺省值」的合法省略也打死**，那是把 31 个槽位的缺陷修成 31+ 个槽位的回归。修法必须**按「有无声明缺省值」分流**：有声明 ⇒ 用声明值；无声明 ⇒ 抛 `ModelRegistryError`。

## 3. 关于「31 槽位 / 24 模型」这个计数 —— 我的一次差点上报的假缺陷

我第一遍测算得到的是 **156 槽位 / 31 模型**，与裁定的 31 / 24 不符。

**差点写下的结论**：「裁定的数字错了」。

**真相**：**两个数都对，数的是不同的东西**。

- 裁定的 **31 / 24** 数的是 **`optional` 槽位**中未声明缺省值者（`opt_no_default = 31`、`len(opt_models) = 24`）；
- 我的 **156 / 31** 数的是 **`required + optional`** 全部槽位中未声明缺省值者。

`required` 槽位**本来就必须由调用方提供**，它们不构成「静默补 0」风险面（调用方不给就是 `KeyError`/缺参，不是悄悄变 0）—— 所以**裁定只数 optional 是对的、更贴合缺陷**，我的全注册表口径反而**高估了风险面**。

**处置**：把自我测算的数当成「裁定错了」，会上报一个**假缺陷**，并诱发对裁定的**无谓更正**。这正是本项目反复出现的同源错误的又一次实例（**先怀疑口径，再怀疑数据**）。本卡 `P-3` 因此把**两个口径并列记录**，并在 `scope_note` 里写明差异来源，而不是抹掉其中一个。

## 4. 缺陷②：`_SIGNED_DRIVERS` 用**名字**决定符号域，而非**语义角色**

**盘上位置**：`scripts/model_registry.py:265-269` 定义，**第 289 行**被查询。

```python
_SIGNED_DRIVERS = frozenset({
    "contract_changes", "other_revenue", "fixed_revenue", "ancillary_revenue",
    "milestone_revenue", "royalty_revenue", "service_revenue",
    "performance_fee_revenue", "fee_revenue",
})
```

**`driver_value_bounds()` 的完整规则顺序**（第 273–293 行，实读）：

1. **显式元数据** `spec.driver_bounds[driver]` ⇒ 用它（`None` 展开为 `±inf`）；
2. `driver == "growth_rate"` ⇒ `(-1.0, +inf)`；
3. **`driver in _SIGNED_DRIVERS`** ⇒ `(-inf, +inf)`（**无界符号**）；
4. `dimension == "ratio"` ⇒ `(0.0, 1.0)`；
5. 否则 ⇒ `(0.0, +inf)`。

**缺陷所在**：第 3 条判的是**驱动名字是否在一张硬编码的字符串集合里**。一个驱动的取值下限能不能为负，取决于**它叫什么名字**，而不是**它在公式里扮演什么角色**。名字集合是**封闭的**：任何新驱动、任何被重命名的驱动，若语义上应当可以有符号，只要名字不在表里，就会被第 5 条**静默钉死在 `(0.0, +inf)`**；反过来，一个语义上不该为负的驱动，只要名字恰好叫 `other_revenue`（或表中其它 8 个），就会获得**无界符号**。

**实测规模**：

- **23 个槽位**的「无界符号」**来自名字**（即：该驱动在 `_SIGNED_DRIVERS` 里，且该模型**没有**对它声明 `driver_bounds`）。
- 涉及的 `dimensions` 分布：`{'revenue': 22, 'backlog': 1}`。
- 第 1 条**显式元数据优先**，所以名字表是**默认**而非**覆盖**：`renewable_generation` 用显式元数据收窄了自己的 `other_revenue` —— 这是**唯一**一个被模型自己收窄的；其余全靠名字表拿符号。

**区分度实测**（`P-5`，同一模型 `unit_sales` 内两个驱动）：

| 驱动 | 是否在名字表 | 实测域 |
|---|---|---|
| `other_revenue` | **是** | `(-inf, +inf)` |
| `units` | 否 | `(0.0, +inf)` |

**同一个模型内，两个驱动因为名字不同而拿到不同的定义域** ⇒ 判据确实是名字，不是角色。

**裁定要求的正确行为**：**基于语义角色的符号规则**（即：由驱动**在公式里的角色**决定可否为负，而非由名字字面量）。

## 5. 立卡内容（裁定的交付物）

裁定说「**两项**同卡处理」⇒ **一张卡、两项缺陷**。以下为可直接派发的内容。

### 卡 id 建议：`I-22-A`（沿用本批 `I-<序>-<字母>` 命名）

**范围**

- **in scope**：`scripts/model_registry.py` 中，**缺陷①的静默补零路径**（`:335`）与**缺陷②的符号判定规则**（`:265-269` 定义 / `:289` 查询）。
- **out of scope**：`_SIGNED_DRIVERS` 之外任何 `driver_bounds` 显式元数据的语义调整；各模型 `_spec(...)` 公式本身；`ratio` / `growth_rate` 两条既有分支（除非语义角色规则需要重述它们）。
- **硬约束**：**必须保持「显式元数据优先」**（现第 1 条）。语义角色规则是**默认域**，不得越权覆盖模型自己的声明。

**验收判据**

*缺陷①*

1. 对**未声明缺省值**的 optional 驱动，**省略**该驱动 ⇒ 抛 `ModelRegistryError`（**不是**补 0）。
2. 对**已声明缺省值**的 optional 驱动，**省略** ⇒ **仍取声明值**，且**不得抛错**（防回归，见 §2 边界情况）。
3. `required` 驱动省略 ⇒ 保持既有抛错行为不变。
4. **不可失败性检查**：新用例必须**在旧代码上会红**（旧代码补 0 ⇒ 不抛 ⇒ 用例失败）。**必须实测**这条，不能只声明。

*缺陷②*

5. 存在一条**由角色驱动**的符号规则，且对 `_SIGNED_DRIVERS` 中**每一个**成员，新旧规则**给出相同的域**（等价性证明，防行为漂移）。
6. 构造一个**名字不在旧表、但语义角色应当可以有符号**的驱动，新规则下 ⇒ 获得有符号域（旧规则下被钉死 `(0.0,+inf)`）。**这条是「规则真的换成角色了」的判据**；只做 5 而不做 6，改为角色规则这件事**未被验证**。
7. 对**语义上不该为负**的驱动（如 `units`、`quantity` 类）⇒ 域**不含负值**，与旧行为一致。
8. `renewable_generation.other_revenue` 的**显式收窄必须仍然生效**（显式优先不回归）。

**每张卡须自备的新 oracle**

- 缺陷①：一张「**驱动 × 是否声明缺省值 × 是否省略**」的三维真值表（至少覆盖 4 类：未声明+省略（→抛）、未声明+给出（→正常）、已声明+省略（→取声明值）、已声明+给出（→用给出值）），**运行前冻结**其期望。
- 缺陷②：一张「**驱动名 × 语义角色 × 期望域**」表，**必须包含至少一个名字不在旧表、角色应有符号**的正例（判据 6 的载体）。

**卡的 provenance 要求**（沿用本批惯例）

- 生成器代码与 oracle 的 **sha256 在运行前落盘**；产物 `mtime` 晚于 oracle；
- 变异臂：删掉/改掉判据的核心断言 ⇒ 该卡闸**必须转红**（本卡已示范，见 §6）；
- **不得**以「用例通过」代替「用例在旧实现上失败」。

## 6. 本卡自身的可失败性（双向负控）

「验证器写了」 ≠ 「验证器会红」。本卡对每个命题都做了**负控**（在**副本**里改坏被测对象，**绝不碰真文件**），要求**正好变红**：

| 负控 | 做了什么 | 期望 | 实测 |

| NC-1 | 宣称「省略与显式 0 不可区分」为**假**（假装缺陷不存在） | P-4 红 | **rc=3，P-4 红** ✅ |
| NC-2 | 要求「裁定计数 == 全注册表计数」（假装两个口径相同） | P-3 红 | **rc=3，P-3 红** ✅ |
| NC-5 | 让显式 0 臂**偏移** `+[1.0]`（两臂真分离） | P-4 红 | **rc=3，P-4 红** ✅ |
| NC-4 | 把修好的 P-6 判据**改回全文扫描** | P-6 红 | **rc=3，P-6 红** ✅ |
| NC-3r | 宣称「名字表与符号无关」（两驱动共享无界域） | P-5 红 | **rc=3，P-5 红** ✅ |
| NC-3r2 | 交换两臂（用 `other_revenue` 的域去判 `units`） | P-5 红 | **rc=3，P-5 红** ✅ |

## 7. 本轮我自己犯的两个错（写下来，不美化）

### 错 1：又一次**凭印象写 API**（与上一轮同一坑）

我先写下 `mr.calculate_model(...)` ⇒ `AttributeError: module 'model_registry' has no attribute 'calculate_model'`。

**值得记的一点**：上一轮我**刚把这条教训写进 skill 陷阱 #27**（「判据必须按被测对象真实形态写 —— 接口靠读源码定，不靠印象」），本轮**又犯了**。⇒ **「写进 skill」不等于「下次会用」**。写下不等于内化。

### 错 2：P-6 的判据**范围搞错**，而且是「**永远不可能通过**」的那种错

我最初的 P-6 写的是：

```python
"ruling_does_not_authorise_the_fix": not bool(re.search(r"授权(修复|实施|改写)", flat))

```

它**红了**。按「**闸红了先分类**」（是数据错还是闸错）：这次是**闸错**。

**原因**：`授权实施` 在 `OWNER_DECISIONS.md` 里**确实出现 2 次**，但**位于 T1-26 与 T2-1**，与 T1-22 无关。**全文扫描**把**别的 TIER 的授权**算进了 T1-22 的判据 ⇒ 这条判据**无论 T1-22 怎么写都不可能变绿**。

**这不是「不能失败的测试」，而是它的镜像：一条「不能通过的测试」** —— 它同样不是测试，是一个常量（恒 `False`）。

**修正**：把判据**收窄到 T1-22 自己那一行表格**（正则先切出 `| T1-22 | ... | ... |`），只对该行文本判「授权立卡」与「未授权修复」。修正后 P-6 绿，且 **NC-4（把判据改回全文扫描）正确转红** —— 证明修复是真的。

**教训**：**判据的范围（scope）和被判的对象一样重要**。裁定是**逐 TIER** 的；跨 TIER 的同名措辞不构成对本 TIER 的裁定。这与本项目既有的「范围」类错误（第 17 次同源）同源。
