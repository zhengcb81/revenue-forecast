# 三项目历史承诺独立复审

审查日：2026-09-19。范围：revenue-forecast、filing-fetch、company-wiki 的历史 planning-with-files 正文、子计划、归档、审查卡和关联证据。root 与三名独立代理完成分区审查和第二波交叉复核。本轮只生成审计材料及隔离反例，没有实施产品修复；新计划中的修复仍待执行。

## 结论

真实场景失败，并不意味着过去所有修复都无效，也不能全部归因为新需求。历史中同时存在：真实修复、有限范围通过、实现未进入生产配置、原目标被执行卡收窄、通过条件被后续摘要扩大、已诚实声明未完成的规划，以及当前仍能复现的缺陷。反复发生的核心问题是：验收对象逐渐从“用户能完成一次研究”变成“某个工具、卡片或证据格式符合要求”，而不同层级的成功又被合并成整体完成。

9 月 18 日启动、19 日续跑的实战已经提供直接结果：围绕紫金矿业、小米、微软执行了 13 次前置流程及诊断命令，正式收入预测交付 **0/3**。这些命令包括 catalog status，并非 13 次完整预测。紫金既有年报可以复用；小米和微软新原件已下载并保存，但扫描/注册未闭合；预测备料又被审核状态、衍生物绑定等门阻断。不能把这些结果概括为“下载器全部坏了”，也不能用计算引擎测试绿色证明完整研究可交付。[原实战报告](../../audit_review/2026-09-18_real_company_skill_audit/AUDIT_REPORT.md)

## 三条可追溯的失效链

### 1. 下载成功，为什么下次仍找不到

原计划已要求 `fetch → canonical commit → scan/assert → re-resolve`。当前真实配置的 v2 扫描缺 adapter，产生 `completed_with_errors`、`files_seen=0`。writer 没有把扫描失败作为注册失败传播，末端显示身份解析错误。小米和微软原件及 source.json 的 hash 存在，却没有对应的 sources/documents/locations/assertions 注册。因此重试复用仍失败。这里应修复注册和错误传播，并用已下载原件验证恢复；再次下载不会解决缺 adapter。

历史依据：8/9 FCAP `task_plan.md:180`、`findings.md:452`；当前依据：实战报告及 wiki 独立配置审查。对照账本：[8/9 逐文复审](reviews/aug09_plans/manual_cases.json)、[wiki 复审](reviews/wiki)。

### 2. 工件和审核门加得更严格，为什么研究反而停住

schema、来源 hash、生成器版本、审核状态等门有正当用途，历史确实修复了多处错误信任。但 producer、consumer、审核 writer 和队列没有作为同一条成功路径验收。FC-901 在 fixture 上通过后，FC-906 首次真实 dry-run 才发现 7718 工件全部不可绑定；修好 schema 后又发现时间格式、列/metadata 和 derived root 问题。随后人工准备的 canary 可以返回选中的 normalized，证明绑定和选择修复有价值；当前独立源码复核确认 `artifact_read` 只是角色列表，尚不能据此证明真正读取工件内容。当前新样本仍可能在 `not_reviewed` 提前退出，后续补料/审核队列并未实际接到需求。

应同时验证正确拒绝和可执行的恢复路径。单纯删除门或手工写 `not_detected` 都没有完成原用户目标。

### 3. 为什么独立审查也能通过

不同代理确实多次发现并修好了真实问题：CLI 缺参数、错误 gap 包装、DAG 祖先方向、无 location 队列饿死、producer 字段不一致、UTF-8、假 mutation 等。不应否认这些成果。

但代理独立不等于验收命题独立。若 reviewer 只按已经收窄的卡片重放同一 fixture，或只验证 accepted/40 位 hash/文件存在，也会错过原需求。旧制度要求所有 commands 的 rc=0，甚至诱发把预期失败的原始 rc 移到自然语言结果里。今后应保留 raw rc，并另列 expected rc 与判定，而不是修改观测事实。

本轮进一步重算：8/13原计划26个内容文件和30个输入快照仍与原hash一致，说明强要求并非因为文件丢失才消失。197场景当前全部标passed，但fixture_hash与oracle均为空；READ10的超时要求指向了不测deadline的artifact测试。精确提取当前closure_report纯函数，仅提供197个passed标签、去掉证据和层级，仍返回closure_ready=true。这个反例只针对该函数，却直接解释了总状态为何能在原业务义务未满足时继续变绿。[原规范至执行卡的独立追溯](reviews/aug13_independent/review.md)

## 收入预测：形式正确仍不等于买方可用

当前 31 模型的隔离核查有 97 tests / 216 subtests 通过，证明被覆盖的公式、输入契约和边界行为；它们不证明预测更准。真实交付还需要同时满足：

1. 收入基线与披露口径一致，分部加总、内部抵销、权益法与合并口径、财政年、汇率和总额/净额均可追溯。
2. 增长由可检验经营驱动解释；不以收入倒推出 GMV 再用 GMV“预测”同一收入，不用主观 confidence 当准确率。
3. 产能、销量、价格、转化、留存、订单确认、渠道库存和爬坡约束进入模型；低/中/高是相互一致的路径，不是任意增长率。
4. 定性研究需列管理层承诺、执行记录、竞争机制、证伪条件、信息缺口，并说明改变哪个具体参数。
5. 生命周期需要显式支持前收入、爬坡、成熟、周期、衰退、转型和并购重组；行业覆盖不能只靠模型名字增加。
6. 准确性必须用冻结信息时点的历史预测和后来实际值比较，按行业、生命周期、预测期限滚动检验，并与简单基准比较。没有该证据不能宣称“准确性提高”。

上轮小米新增业务、微软 Azure、紫金矿业多口径的研究草稿说明了这些要求为何必要；草稿不是经过完整技能链验证的正式预测。本轮不重新核定其中所有公司财务事实。
